# 1. Введение

## 1.1 Назначение документа

Данный документ определяет требования к Web-приложению «TaskFlow — Трекер задач». SRS описывает **что** должна делать система, какие ограничения и показатели качества она должна соблюдать, а также каким способом требования будут проверяться. Документ предназначен для разработчика, тестировщика и заказчика и используется на этапах анализа, проектирования, реализации и проверки программного продукта.

## 1.2 Область применения продукта

«TaskFlow» — Web-приложение для создания, приоритизации и выполнения разовых задач с представлением задач на Kanban/Scrum-доске. Пользователь может создавать задачи, назначать им приоритет и срок, перемещать их между состояниями «К выполнению», «В работе» и «Готово», а также редактировать и удалять задачи. В первую версию входят управление задачами, фильтрация, поиск и сохранение данных. В первую версию не входят повторяющиеся задачи, календарное планирование, командные роли, чат и внешние интеграции.

# 2. Обзор продукта

## 2.1 Перспектива продукта

«TaskFlow» является самостоятельным новым Web-приложением для личного управления разовыми задачами. В рамках первой версии продукт не является частью более крупной информационной системы и не требует внешних бизнес-сервисов. Клиентская часть взаимодействует с серверной частью по HTTP/HTTPS через API, а сервер сохраняет задачи в базе данных. Для реализации проекта используется язык программирования Java; в качестве предпочтительного серверного стека используется Spring Boot. Система рассчитана на локальное или учебное развёртывание.

**Границы системы:**

Пользователь взаимодействует с приложением **TaskFlow** через Web-интерфейс. Обмен данными между пользователем и приложением осуществляется по протоколу **HTTP/HTTPS**.

Приложение **TaskFlow** состоит из Web-интерфейса и Java API. Web-интерфейс предоставляет пользователю возможность работать с задачами, а Java API обрабатывает запросы и реализует бизнес-логику приложения.

Java API взаимодействует с **хранилищем задач**. Между приложением и хранилищем выполняются операции **CRUD**:
- создание задач;
- получение задач;
- изменение задач;
- удаление задач.

Таким образом, граница системы включает **пользовательский интерфейс, Java API и хранилище задач**, а пользователь является внешним участником системы.

## 2.2 Функции продукта

1. Создание разовой задачи.
2. Просмотр задач на Kanban-доске.
3. Изменение названия и описания задачи.
4. Установка и изменение приоритета.
5. Установка срока выполнения.
6. Перемещение задачи между статусами.
7. Удаление задачи.
8. Поиск задач по названию и описанию.
9. Фильтрация по статусу и приоритету.
10. Сохранение и повторное получение данных после обновления страницы.

## 2.3 Ограничения продукта

1. Приложение должно быть реализовано как Web-приложение.
2. Основной язык разработки серверной части — Java.
3. Интерфейс первой версии должен быть доступен в современном браузере на ПК.
4. Данные задачи должны сохраняться в постоянном хранилище, а не только в памяти процесса.
5. Задача в первой версии является разовой; механизм повторения задач не реализуется.
6. В первой версии не требуется интеграция с внешними календарями и сервисами.
7. Требования должны иметь уникальные идентификаторы согласно схеме `REQ-[AREA]-[NNN]`.
8. Графический макет основного экрана хранится в `ui/taskflow-board.png`.

# 3. Требования

## 3.1 Внешние интерфейсы

### 3.1.1 Пользовательские интерфейсы

Основной экран представляет собой Kanban-доску с тремя колонками:

- **К выполнению** — новые и ожидающие выполнения задачи;
- **В работе** — задачи, над которыми пользователь работает;
- **Готово** — завершённые задачи.

Карточка задачи содержит название, краткое описание, приоритет и срок. В верхней части располагаются название приложения, поле поиска, фильтры и кнопка создания задачи.

Графический мокап основного экрана: [`ui/taskflow-board.png`](../ui/taskflow-board.png).

Интерфейс должен обеспечивать:

- однозначное отображение текущего статуса;
- визуальное различие приоритетов;
- сообщение об ошибках ввода;
- подтверждение удаления задачи;
- отображение пустых колонок;
- адаптацию к ширине окна браузера в пределах поддерживаемой версии.

### 3.1.2 Аппаратные интерфейсы

Специальные аппаратные интерфейсы не требуются. Для работы необходим компьютер или другое устройство с современным Web-браузером и сетевым соединением с сервером приложения.

### 3.1.3 Программные интерфейсы

Внутреннее взаимодействие клиента и серверной части выполняется через HTTP/HTTPS API.

| Интерфейс | Назначение |
|---|---|
| `GET /api/tasks` | Получение списка задач |
| `POST /api/tasks` | Создание задачи |
| `PUT /api/tasks/{id}` | Изменение задачи |
| `DELETE /api/tasks/{id}` | Удаление задачи |
| `PATCH /api/tasks/{id}/status` | Изменение статуса |

Формат обмена данными — JSON. При ошибке сервер должен возвращать HTTP-код ошибки и сообщение, пригодное для отображения пользователю.

## 3.2 Функциональные требования

### REQ-FUNC-001 — Создание задачи

- **Statement:** Система должна позволять пользователю создать разовую задачу с названием, описанием, приоритетом и сроком выполнения.
- **Rationale:** Создание задачи является основной функцией продукта.
- **Acceptance Criteria:** После успешного заполнения обязательных полей новая задача появляется в колонке «К выполнению» и сохраняется в хранилище.
- **Verification Method:** Test
- **More Information:** Поля и форма соответствуют `ui/taskflow-board.png`.

### REQ-FUNC-002 — Просмотр Kanban-доски

- **Statement:** Система должна отображать задачи в трёх статусных колонках: «К выполнению», «В работе», «Готово».
- **Rationale:** Доска должна давать пользователю визуальное представление о состоянии работы.
- **Acceptance Criteria:** Каждая существующая задача отображается ровно в одной колонке в соответствии со своим статусом.
- **Verification Method:** Demonstration
- **More Information:** UI-мокап находится в `ui/taskflow-board.png`.

### REQ-FUNC-003 — Изменение задачи

- **Statement:** Система должна позволять пользователю изменять название, описание, приоритет и срок существующей задачи.
- **Rationale:** Пользователю необходимо корректировать план по мере изменения обстоятельств.
- **Acceptance Criteria:** После сохранения изменённые данные отображаются в карточке задачи и сохраняются после перезагрузки страницы.
- **Verification Method:** Test

### REQ-FUNC-004 — Изменение статуса

- **Statement:** Система должна позволять пользователю переводить задачу между статусами «К выполнению», «В работе» и «Готово».
- **Rationale:** Статус отражает прогресс выполнения.
- **Acceptance Criteria:** После изменения статуса задача отображается в соответствующей колонке и сохраняет новый статус после перезагрузки.
- **Verification Method:** Test

### REQ-FUNC-005 — Удаление задачи

- **Statement:** Система должна позволять пользователю удалить существующую задачу после подтверждения операции.
- **Rationale:** Завершённые или ошибочно созданные задачи должны удаляться.
- **Acceptance Criteria:** После подтверждения задача исчезает с доски и отсутствует в списке задач.
- **Verification Method:** Test

### REQ-FUNC-006 — Приоритизация

- **Statement:** Система должна позволять устанавливать для задачи один из приоритетов: «Низкий», «Средний», «Высокий».
- **Rationale:** Приоритет позволяет определить порядок работы.
- **Acceptance Criteria:** Выбранный приоритет отображается в карточке и сохраняется после перезагрузки.
- **Verification Method:** Test

### REQ-FUNC-007 — Поиск

- **Statement:** Система должна позволять выполнять поиск задач по названию и описанию.
- **Rationale:** Поиск сокращает время нахождения нужной задачи при увеличении их количества.
- **Acceptance Criteria:** После ввода поискового запроса отображаются только задачи, соответствующие запросу.
- **Verification Method:** Test

### REQ-FUNC-008 — Фильтрация

- **Statement:** Система должна позволять фильтровать задачи по статусу и приоритету.
- **Rationale:** Фильтрация позволяет сосредоточиться на определённой группе задач.
- **Acceptance Criteria:** При выборе фильтра на доске отображаются только задачи, удовлетворяющие выбранным условиям.
- **Verification Method:** Test

### REQ-FUNC-009 — Валидация ввода

- **Statement:** Система должна проверять обязательные поля при создании и редактировании задачи и показывать пользователю сообщение об ошибке при некорректном вводе.
- **Rationale:** Некорректные данные не должны попадать в хранилище.
- **Acceptance Criteria:** Задача не создаётся или не изменяется, если обязательное название отсутствует или нарушены ограничения формата.
- **Verification Method:** Test

### REQ-FUNC-010 — Сохранение данных

- **Statement:** Система должна сохранять созданные и изменённые задачи в постоянном хранилище.
- **Rationale:** Данные не должны теряться при обновлении страницы или перезапуске приложения.
- **Acceptance Criteria:** После перезапуска приложения ранее сохранённые задачи доступны пользователю.
- **Verification Method:** Test

## 3.3 Качество обслуживания

### 3.3.1 Производительность

- **REQ-PERF-001:** При нормальной учебной нагрузке до 500 задач получение и отображение доски должно занимать не более 2 секунд в 95% запросов.
- **REQ-PERF-002:** Операции создания, изменения и удаления задачи должны завершаться не более чем за 2 секунды в 95% запросов при доступном сервере.

### 3.3.2 Безопасность

- **REQ-SEC-001:** Сервер должен проверять входные данные до их сохранения.
- **REQ-SEC-002:** API не должен выполнять переданные пользователем строки как программный код или SQL-команды.
- **REQ-SEC-003:** При передаче данных по сети в рабочем развёртывании должен использоваться HTTPS.
- **REQ-SEC-004:** Ошибки API не должны раскрывать пользователю служебные данные, пароли или строки подключения к базе данных.

### 3.3.3 Надёжность

- **REQ-REL-001:** При ошибке сохранения данных система должна сообщить пользователю об операции, которая не была выполнена, и не должна показывать операцию как успешно сохранённую.
- **REQ-REL-002:** При временной недоступности хранилища система должна возвращать контролируемую ошибку вместо аварийного завершения пользовательского запроса.

### 3.3.4 Доступность

- **REQ-AVAIL-001:** В учебном развёртывании приложение должно быть доступно в течение времени демонстрации лабораторной работы, кроме заранее объявленных перезапусков.

### 3.3.5 Наблюдаемость

- **REQ-OBS-001:** Сервер должен записывать в журнал факт запуска приложения и ошибки обработки запросов.
- **REQ-OBS-002:** Журналы не должны содержать пароли и иные секреты.

## 3.4 Соответствие стандартам

- **REQ-COMP-001:** Исходный код и документация проекта должны храниться в системе контроля версий Git.
- **REQ-COMP-002:** Идентификаторы требований должны быть уникальными и использоваться в тестовых материалах.
- **REQ-COMP-003:** Документация требований должна быть оформлена в Markdown согласно предоставленному шаблону SRS.

## 3.5 Проектирование и реализация

### 3.5.1 Установка

- **REQ-INST-001:** Приложение должно запускаться в поддерживаемой среде Java без ручного изменения исходного кода.
- **REQ-INST-002:** Параметры подключения к хранилищу должны задаваться конфигурацией окружения или файлами конфигурации, а не быть жёстко зашиты в исходный код.

### 3.5.2 Сборка и поставка

- **REQ-BUILD-001:** Проект должен собираться стандартным инструментом сборки Java-проекта.
- **REQ-BUILD-002:** Сборка должна позволять получить запускаемый артефакт приложения и выполнить тесты.

### 3.5.3 Распределение

- **REQ-DIST-001:** Для лабораторной версии допускается развёртывание на одном сервере или локальном компьютере.
- **REQ-DIST-002:** Клиентская часть должна обращаться к серверу через единый адрес приложения.

### 3.5.4 Сопровождаемость

- **REQ-MAINT-001:** Код должен быть разделён на логические компоненты для UI, бизнес-логики и доступа к данным.
- **REQ-MAINT-002:** Публичные API и нетривиальная бизнес-логика должны иметь краткие комментарии или документацию.
- **REQ-MAINT-003:** Изменения требований должны отражаться в истории изменений SRS.

### 3.5.5 Повторное использование

- **REQ-REUSE-001:** Общая логика валидации и работы с задачами должна быть реализована без дублирования в разных обработчиках.

### 3.5.6 Переносимость

- **REQ-PORT-001:** Серверная часть должна запускаться на поддерживаемой Java Runtime Environment.
- **REQ-PORT-002:** Пользовательский интерфейс должен работать в современных версиях Chrome, Firefox или Edge.

### 3.5.7 Стоимость

- **REQ-COST-001:** Для лабораторной версии должны использоваться доступные без отдельной коммерческой лицензии инструменты и библиотеки.

### 3.5.8 Сроки

- **REQ-DEAD-001:** Первая рабочая версия должна включать CRUD задач, Kanban-доску, приоритеты, поиск, фильтрацию и сохранение данных к моменту защиты соответствующей лабораторной работы.

### 3.5.9 Доказательство концепции

- **REQ-POC-001:** До реализации полного приложения должна быть продемонстрирована работа основного сценария: создание задачи → изменение статуса → завершение задачи.
- **Критерий успеха:** пользователь может пройти сценарий без потери данных, а карточка задачи перемещается между колонками.

### 3.5.10 Управление изменениями

- **REQ-CM-001:** Каждое изменение утверждённых требований должно быть зафиксировано в SRS и истории изменений.
- **REQ-CM-002:** Изменения, влияющие на состав функций или архитектуру, должны быть проверены до включения в основную ветку.
- **REQ-CM-003:** Для лабораторного проекта разработка требований и документации должна выполняться в отдельной Git-ветке с последующим Pull Request.

## 3.6 ИИ/МО

ИИ/МО в первой версии продукта не используется.

# 5. Приложения

## Приложение A. Основной сценарий пользователя

1. Пользователь открывает приложение.
2. На доске отображаются существующие задачи.
3. Пользователь нажимает «+ Новая задача».
4. Вводит название, описание, приоритет и срок.
5. Сохраняет задачу.
6. Задача появляется в колонке «К выполнению».
7. Пользователь переводит задачу в «В работе».
8. После выполнения переводит задачу в «Готово».
9. При необходимости пользователь редактирует или удаляет задачу.
